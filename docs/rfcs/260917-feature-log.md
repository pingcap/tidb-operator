# Feature log generation

Feature constants and their histories in `api/meta/v1alpha1/feature.go` are the
inputs for generated feature histories. Definitions are private constants whose
values are irrelevant to feature identity:

```go
const (
    // Example description.
    //
    // +feature:unreloadable=
    // +feature:log=rev=0,stage=ALPHA,default=false
    // +feature:log=rev=1,stage=BETA,default=true
    _Example = iota

    // Another feature.
    //
    // +feature:unreloadable=
    // +feature:log=rev=0,stage=ALPHA,default=false
    _Another
)

```

The generator removes the leading underscore from each private constant name
(`_Example` becomes `Example`). It also generates `_ = _Example` references
to keep the source constants used without lint exemptions. Numeric iota values
are never part of the log or hash; revisions come only from the markers. No build constraint is needed.

Run `make featuregen` and commit the generated files. No previous generated files
are needed to rebuild the log. The feature constants, their descriptions, the enum
annotation, and current stage constants are generated together in
`api/meta/v1alpha1/zz_generated.features.go`. Shared API structures remain in
`feature_types.go`. Generated constants and enum values follow source declaration
order; only hash snapshots are sorted by feature name.

## Revisions

Revisions start at zero and are globally contiguous. All changes with the same
revision form one atomic entry. Within a feature, revisions must strictly
increase. A published revision cannot be changed, including by adding another
feature to it. When concurrent branches append the same next revision, rebase
and place the later change in a new revision.

The marker requires exactly `rev`, `stage`, and `default`. Parameter order and
surrounding whitespace do not affect the hash. ALPHA requires default=false;
BETA and STABLE require default=true. DEPRECATED forbids explicit configuration
and its default states whether the retired capability stays enabled. Features
may advance stages or become deprecated; DEPRECATED is terminal. Keep deprecated
constants and all their historical records.

## Hash protocol

For each revision, replay all changes through that revision and sort the complete
feature definitions by the UTF-8 bytes of the feature name. Serialize this exact
structure with Go's `encoding/json.Marshal`, preserving the field order:

```json
{"prevHash":"","features":[{"name":"Example","stage":"ALPHA","default":false}]}
```

The first revision uses an empty prevHash. Later revisions use the preceding
entry's `sha256:`-prefixed, lowercase hexadecimal hash. The current hash is
`sha256:` followed by the lowercase hexadecimal SHA-256 digest of the JSON bytes.
All fields are present, including false defaults. There is no indentation or
trailing newline. Feature names are ASCII alphanumeric, starting with an uppercase
letter. Stage names are the uppercase strings above.

Field order, names, representation, and interpretation are immutable protocol
choices. Golden tests pin both the bytes and hashes for a multi-revision history.
Ordinary comments, Go identifiers, source declaration order, and timestamps are
not hash inputs. Different histories produce different hashes even when their
final feature definitions are identical.

The generated `logs = [][]FeatureLog` stores the complete snapshot at every revision.
`hashToRev` maps each hash to its snapshot index. Previous hashes and the JSON hash
input structure are used only by the generator. Stage values reference fixed meta
stage constants, preserving historical stages independently of the current stage.
`features.DefinitionsAt(hash)` returns an isolated copy and rejects unknown hashes.
`features.CurrentFeatureGateDefinitionHash` identifies the latest revision.
Generation alone does not change the operator's runtime feature resolution.

## Generation and tests

`make featuregen` builds the generator with `hack/build.sh`, then uses gengo to
load the API package and write the three generated Go files. It uses the shared
Go boilerplate and the `ignore_autogenerated` build tag. Source AST parsing
preserves declaration order and validates feature markers.

`go test ./cmd/feature-gen ./cmd/feature-log-lint ./pkg/features` covers parsing, stable hashes,
history comparison, reconstruction, and snapshot lookup.

## Lint entry point

`hack/lint.sh` accepts `golangci` or `feature-log`; multiple names are allowed
and no names defaults to all checks. `make lint` and `make lint/feature-log`
build the required tools and invoke this entry point. `make fix/lint` continues
to invoke golangci-lint directly with `--fix`. For direct invocation of the script,
the binaries must already exist in `V_BIN`.

## Append-only lint

Run `make lint/feature-log V_REPO_REF=<branch-or-commit>` to fetch the
baseline repository and compare generated logs. `V_REPO_REF`, `V_REPO_URL` and
`V_REPO_DIR` are defined in `hack/lib/vars.sh` and accept environment overrides. The default is `main`; PR CI
supplies the target branch SHA. `V_REPO_URL` defaults to the upstream
TiDB operator repository and can be overridden for forks or local testing.

`make fetch/old-version-repo V_REPO_REF=<branch-tag-or-commit>` fetches
only the old-version checkout. Both this target and upgrade e2e use
`hack/lib/repo.sh`, caching checkouts under `_output/old-version-repo`.
Every invocation fetches the requested revision; a failed fetch stops the caller
instead of falling back to stale logs.

The standalone `cmd/feature-log-lint` command accepts `--root` and `--base-root`:

```sh
go run ./cmd/feature-log-lint --base-root=_output/old-version-repo/main
```

Lint parses `pkg/features/zz_generated.feature_log.go` from the working tree
and the fetched base repository using Go AST. It compares each snapshot's feature constant,
stage constant, and default value. Formatting, field order, and entry order do
not affect comparison. The generator retains its own source parser and hash
implementation; lint does not share a package with it.

All existing revision snapshots must remain identical. Unchanged histories pass;
otherwise the entire PR must append exactly one revision, whose index is the
number of revisions in the base. Multiple feature changes must share that index.
Removing revisions, inserting changes into published revisions, or appending
multiple revisions fails. The generator validates source revision gaps, invalid defaults, redundant entries,
and stage transitions. Existing generation verification checks that generated
files match their source, including hashes; this lint only checks the logs.

Other declarations, including hash indexes and unreloadable metadata, are ignored.
Lint requires no API source or component catalog. If the base repository exists
but its generated log file is absent, it predates feature logging and is treated
as an empty history. Initial adoption may append only rev 0. A missing base
repository, missing current log file, other read errors, or malformed existing
logs still fail. If another PR uses
the next revision first, update the target baseline and move this PR's new entries
to the next index. Re-run CI against the latest target commit before merging.

## Constructing feature gates

`NewFromHash(hash)` reconstructs the default-enabled gates at the requested
revision. Empty and unknown hashes return errors, rather than falling back to the
current defaults.

There are three gate configurations:

- Group/Instance gates (`NewFromObject` and `NewFromFeatures`) use only their complete
  `spec.features` lists. They never read defaults.
- Default gates are constructed once in `defaultGates`. Historical defaults are
  available through `NewFromHash(hash)`.
- Cluster gates (`NewFromCluster`) use `spec.featureGates` as overrides over current
  defaults. `NewFromClusterWithHash` uses the defaults from a specific historical hash.

Cluster feature entries have an optional `enabled` field with default true.
Omitting an entire feature uses its default; including `{name: FeatureA}` enables
it, and `{name: FeatureA, enabled: false}` disables it. Overrides are copied by
value so caller mutations cannot affect constructed gates or shared defaults.

`ClusterFeatures` materializes the effective enabled list for propagation to
Groups/Instances, including default-enabled features and excluding explicit false
entries. `coreutil.EnabledFeatures` uses this same resolution, so propagation,
sync checks, and runtime decisions agree.

## Restart requirements

Declare components that cannot reload a feature in its source comment:

```go
// +feature:unreloadable=tikv,pd
// +feature:log=rev=0,stage=ALPHA,default=false
_Example = iota
```

`+feature:unreloadable=*` includes every `Component` constant in
`api/meta/v1alpha1/types.go`, including components added later. Explicit names use
those constants' string values, such as `tikv-worker` or `resource-manager`.
The marker is required on every feature. Use `+feature:unreloadable=` explicitly
for an empty component list; omitting the marker fails generation.
Unknown names, duplicate names or markers, and a wildcard mixed with names fail
generation.

`make featuregen` produces `pkg/features/zz_generated.reload.go`, referencing meta
feature and component constants. Entries follow feature declaration order and
component lists are sorted by name. Every feature gets an entry. Restart metadata
is separate from the stage/default history and does not change its hashes.

## Cluster status checkpoint

`status.featureGatesHash` records the adopted feature-definition hash. The Cluster
controller persists the current hash after loading its context and before
changing finalizers, propagating features, or reconciling Services and other
status fields. A failed write, conflict, or a response with the field pruned stops
that reconcile. The context is updated only after persistence succeeds. When the
hash already matches, the controller proceeds without another checkpoint write.
Paused Clusters retain their existing pause behavior and perform no reconciliation
writes. This checkpoint does not replace the operator startup compatibility check.
